# 工程化实施路线

日期：2026-10-30。依据：RAG_PROJECT_AUDIT.md 与当前源码。状态：阶段 1 已完成本地与远端 CI 验收；阶段 2 已完成本地验收。后续阶段仍为计划，不表示相应能力已经完成。

## 目标与范围

第一目标是交付一个别人能安装、故障可处理、结果可追溯、运行可排障的单实例 RAG 应用。先完成现有单规范场景的可靠交付；多人服务与多文档能力按需求扩展。保持当前 Hybrid + bounded Agent 主流程，不以增加框架作为工程化验收条件。

## 阶段 1：可复现基线（估计 1–2 个工作日）

工作：
- 选择一个实际验证的 Python 基线版本，建立独立虚拟环境，处理现有缺包与 NumPy/SciPy 兼容问题。
- 选择一种依赖锁定方式，提交锁文件；明确开发、运行与模型资源准备步骤。
- 将测试分为离线单元测试、真实 PDF 集成测试、需模型/API 的显式手动评测；通过标记选择，不能用默认跳过掩盖本应通过的测试。
- 对项目直接使用的依赖显式声明，避免依赖其他包偶然带入。
- 建立 CI：安装、轻量静态检查、离线测试；PDF 集成检查按数据可用性明确配置。

涉及：pyproject.toml、依赖锁文件、tests、CI 配置、README。

验收：在干净环境按文档安装并运行；离线测试无需 API 密钥且通过；需外部资源的测试有清楚入口；记录实际结果。远端 CI 只有运行通过才算验收。

完成记录（2026-10-30）：Windows / Python 3.12.16 使用 `uv.lock` 清空并重建环境成功；Ruff 通过；离线测试 `55 passed`；integration `9 passed, 5 subtests passed`；sdist 与 wheel 构建成功。远端 Windows / Python 3.12 GitHub Actions 首次运行全部通过：[Reproducible baseline #1](https://github.com/WangYDING/-Agentic-RAG-/actions/runs/40997691755)。

## 阶段 2：应用包与配置（估计 1–2 个工作日）

工作：
- 将 BM25Retriever、HybridRetriever 及必要融合函数移到 src 内；eval 反向导入正式实现。
- 使用一个统一工厂构建完整 Agent，Web 与 CLI 共用配置与错误契约；明确基础 RAG CLI 的保留用途。
- 集中管理 PDF/索引路径、模型、检索参数、请求预算；在应用边界加载环境变量并验证，避免模块导入时分散加载。
- 明确安装包、CLI 和 Web 启动方式；核心业务保持可注入组件。

涉及：agent_demo.py、app.py、src、eval、pyproject.toml。

验收：正式应用不导入 eval runner；构建并安装 wheel，在源码目录之外验证组件和入口；使用替代组件验证 CLI/Web 共用编排，真实模型验证独立进行。

本地完成记录（2026-10-30）：BM25、Hybrid 与 RRF 已迁入 `src`，应用不再导入 `eval`；配置优先级、默认值和缺项提示的离线测试通过；CLI/Web 共用 `src.application.build_agent_workflow`。Ruff 通过，离线测试 `59 passed`，integration `9 passed, 5 subtests passed`。wheel 已安装到仓库外的独立临时环境，包导入、`engineering-rag --help`、`engineering-rag-web --help` 和无密钥错误契约均通过；未调用真实模型或收费 API。

## 阶段 3：可靠输出与失败处理（估计 2–3 个工作日）

工作：
- 定义正常回答、证据不足拒答、依赖故障三种外部结果，保留 request_id 和可解释错误。
- 引用校验在展示前执行；处理缺少引用、未知编号和 provenance 不完整。校验失败先采用不返回正常答案的明确策略，需要时再增加最多一次修复，并纳入总预算。
- Grader 增加字段间一致性检查；非法 JSON、空响应或不一致输出作为判定故障处理，不伪装成证据不足。
- 模型调用显式配置超时、重试范围与次数，考虑 SDK 重试，避免重复叠加；定义一次问答的总时长和调用次数预算。
- Web/CLI 统一捕获可预期错误；给出明确提示，日志保留排障信息。

涉及：src/evidence.py、src/evidence_sufficiency.py、src/agent_workflow.py、src/generator.py、src/query_rewriter.py、入口适配层。

验收：针对成功、业务拒答、非法引用、无引用、超时、限流、空响应、非法 JSON 的故障注入检查通过；业务补充检索仍最多一次；失败结果不作为正常答案显示。引用格式通过不表述为事实正确。

## 阶段 4：索引可靠性（估计 2–3 个工作日）

工作：
- 分离离线构建和在线读取，提供显式构建/重建入口，保留方便演示的首次构建模式。
- 以文档身份和构建配置标识索引版本，避免同名文件和不同配置竞争同一位置。
- 增加构建互斥；临时版本完成后校验，再通过适合 Windows/Linux 的原子发布方案更新活动版本，读请求使用完整快照。
- manifest 记录产物校验、模型/解析版本；建立损坏检测与恢复策略。
- 构建失败保留上一有效版本；有新版本后明确刷新 Web 缓存，避免长期使用旧索引。

涉及：src/index_manager.py、src/vector_store.py、应用工厂、索引构建入口。

验收：模拟构建中断、产物损坏、并发构建、同名文档和配置变更；不会加载混合版本；失败不破坏旧版本；发布后能显式切换到新索引。

## 阶段 5：观测与部署（估计 2–3 个工作日）

工作：
- 记录 request_id、索引/模型版本、各阶段耗时、重试、最终状态和错误类型；可获取时记录 token 用量，成本按已配置费率估算并标记为估算。
- 默认不记录密钥、完整文档和问题正文；为调试内容设置明确开关。
- 构建单实例容器和启动说明，明确模型下载/预热、资源需求、密钥注入、索引持久卷与备份恢复。
- 区分进程存活与服务就绪；检查索引和本地模型状态，不用每次健康检查调用收费模型 API。
- 记录冷启动、热启动与端到端耗时；确定目标硬件和使用人数后制定延迟/并发目标，并测量是否达到。

涉及：日志与指标模块、Dockerfile、启动/部署配置、README 或部署文档。

验收：干净环境容器可启动；重启无需重建已有效持久化索引；可用 request_id 定位失败；完成一次索引恢复和最小真实问答验证，记录实际成本与结果。

## 阶段 6：质量回归与首个可靠版本（估计 1–2 个工作日）

工作：
- 保存当前数据和结果作为历史基线，新增开发用质量回归集，覆盖普通问题、缺证据、部分支持、多证据与表格。
- 固定数据版本、配置、模型标识和产物版本；在有 Git 元数据时记录提交标识。
- 增加答案完整性/证据支持的人工复核样例，区分引用合法性和事实正确性。
- 使用新独立测试集验收质量变化，不反复用现有 test_v1 调参。
- 每个版本运行离线检查；模型相关评测按显式入口和预算执行。

验收：有可复现测试报告、模型评测报告、已知限制、启动说明和恢复说明；预先声明可接受退化范围，超限须解释或修复后发布。

## 后续：确有多人服务需求时实施

- 增加薄 API 适配层，复用相同应用服务；定义问答、索引状态及健康接口。
- 增加认证、请求大小限制、限流、并发容量控制与超时取消；禁止客户端任意指定服务器文件路径。
- 根据请求负载决定队列/进程模型，先验证模型对象及缓存的并发行为。
- 多文档上线前定义文档权限、规范版本和证据身份；需要按身份过滤检索时必须在服务上线前实现。
- API 契约、权限隔离、并发压测和故障恢复通过后，才承诺多人可用。

不在第一轮范围：微服务拆分、Kubernetes、自由规划、多 Agent、GraphRAG、分布式向量库。只有容量或质量证据说明需要时再评估。

## 时间与执行约束

阶段 1–6 粗估共 9–15 个有效工作日，按一人熟悉项目、已有模型/API 资源计算；不包含大规模数据标注、GPU 采购、多文档权限系统或生产组织流程。此估计不是已安排的日程。每阶段完成验收再进入依赖阶段；较大的代码搬迁与行为改动分开提交，便于定位回归。

建议首个实施切片仅做阶段 1：先得到可复现的绿灯基线，再移动代码或修改回答策略。
