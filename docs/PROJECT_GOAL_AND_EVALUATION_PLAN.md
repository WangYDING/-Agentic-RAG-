# 当前项目唯一目标：可追溯的多规范查询

状态：2026-11-07 确立的目标与验收方案。本文约束后续新工作范围；既有 `ENGINEERING_ROADMAP.md` 保留为工程化历史记录，已冻结的独立集及门槛不因本文重写。当前 checkout 落后于 Notion 工程日志所记录的 2026-11-06 多规范实现和独立验收，下面的实施顺序是逻辑依赖，不表示每项仍未完成。

## 目标与完成定义

交付一个面向工程规范查询的单实例系统：用户可指定规范及版本，或在受控规范集合中查询；系统给出有原文来源的答案，在证据不完整或适用版本不明确时说明缺口。首版选择同一专业中 3 份有可靠来源、允许使用且彼此相关的规范；只有取得可核验的版本与生效信息时才支持“按日期有效版本”判断，不推断或编造规范效力。

完成的判断同时满足三项：

1. 真实查询能区分文档、版本、条文、表格和页码；跨文档同号条文不串引；文档更新后的索引快照可追溯。
2. 通过“检索 → 最终上下文 → 生成 → 端到端”四层评测与逐题 bad case 归因，报告同时给出质量、延迟和调用量，并绑定代码、数据、文档、索引与模型配置。
3. 在预先声明门槛的新独立集上完成一次验收，保存逐题输出与人工复核；README 给出可复现启动方式、六类代表性查询和诚实的适用边界。

首版为受控单实例查询应用。设计文件合规审查、多轮追问、公开多人服务、复杂权限、多 Agent、GraphRAG 与微服务不属于本目标的交付条件。已有能力可继续保留，但不以新增这些能力作为本轮进度。

## 唯一评测框架

每题统一包含：问题、查询范围、是否可回答、允许的文档/版本、gold 位置、必要事实点、关键答案点、数值/单位/条件、不可回答原因与审核身份。文档来源和适用版本必须可核验。开发集用于失败分析和调参；独立集先冻结数据、代码候选和门槛，再运行。AI 辅助标注披露身份；答案的最终质量需要独立人工复核。

| 层 | 测什么 | 主指标与输出 |
|---|---|---|
| 检索 | 过滤后候选是否找到正确文档、版本和必要条文 | 文档/版本选择正确率、Recall@K、MRR、逐题漏召回；保留现有 Dense/BM25/RRF 对照 |
| 最终上下文 | 送入 Generator 的证据是否包含全部必要事实、条件、表注，是否混入过多无关片段 | 必要事实完整覆盖率、多证据完整覆盖率、上下文长度、无关证据占用；保存受控评测快照 |
| 生成 | 给定上下文时答案是否答对、答全，每项事实是否有对应证据 | 要点完整性、数值/单位/适用条件正确性、逐项证据支持与引用解析；按现有 0/1/2 量表人工评分 |
| 端到端 | 用户最终得到回答、合理拒答还是服务错误 | 错误接受、错误拒答、服务错误、任务成功、p50/p95 延迟、token 与可信费率下的估算成本 |

系统内的 Evidence Sufficiency Grader 是被评测对象，不作为自身结果的独立评委。固定证据包继续测试它的误判充分/不足；自动 evaluator 优先使用可确定的身份、覆盖、引用和预算检查。可选 LLM 评委只用于辅助筛查，需与人工样本校准，不能单独签署验收。

一题失败按最早偏离环节归因：原文解析、文档/版本过滤、候选召回、最终上下文、充分性判定、生成、引用、外部服务。bad case 记录题目、期望、实际、原文与请求证据、根因、修复和回归结果。修复保留到开发回归集，不能继续用已看过的独立结果声称独立泛化。

## Baseline 与数据门槛

- 第一条 baseline 是上述第 0 步收口的单规范候选，记录旧集结果与质量/性能；历史 `test_v1` 仅作历史对照。
- 多规范开发集先覆盖指定文档、全库发现、同号条文、版本筛选、跨文档组合、表格/条件、部分支持和不可回答。按类别报告分母与逐题失败，不只报总体均值。
- 多规范独立集从不同问题表述与未用于调参的证据位置构建；在首次运行前冻结文件哈希、预设门槛、候选提交和配置。文档或版本误引、核心数值/条件错误、无证据核心结论设为硬性失败；可回答率、完整性和延迟门槛根据开发基线与目标硬件先确定，不事后改线。
- 每次优化只改变一个主要因素，在同一开发集和运行条件下对照 baseline 的质量、延迟与 token。对模型随机性或服务漂移作重复测量与记录；差异不自动归因于代码。
